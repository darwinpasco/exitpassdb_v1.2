# ExitPass DB Object Source Coverage / Equivalence CI Result v1.0

## Result
PASSED. The database repository now has CI-ready coverage and equivalence reporting plus a PostgreSQL service-container full apply job for the ExitPass object-source layout.

## Scripts added or updated
| Script | Purpose |
| --- | --- |
| `scripts/validation/Invoke-DbObjectSourceCoverageReport.ps1` | Produces JSON and Markdown coverage reports, validates schema coverage, apply-order coverage, generated SQL freshness, required object presence, and disposable DB apply. Supports local Docker `docker exec` mode and direct `psql` mode for CI service containers. |
| `scripts/validation/Invoke-DbObjectSourceCiCheck.ps1` | Single CI/local entry point that runs generators, existing layout validators, and the coverage/equivalence report. Passes DB connection parameters through to the report script when `-RunDbApply` is used. |

## Report output paths
| Output | Notes |
| --- | --- |
| `build/reports/db-object-source-coverage.json` | Machine-readable report for CI/artifact processing. |
| `build/reports/db-object-source-coverage.md` | Human-readable report for local review and CI artifacts. |

`build/reports/` is ignored because reports include run metadata and should be generated by local validation or CI, not edited by hand.

## CI workflow behavior
Updated `.github/workflows/db-object-source-validation.yml`.

| Job | Runner | Purpose |
| --- | --- | --- |
| `db-object-source-validation` | `windows-latest` | Fast non-DB validation using `Invoke-DbObjectSourceCiCheck.ps1 -SkipDbApply`, then `git diff --check`. |
| `db-object-source-postgres-apply` | `ubuntu-latest` | Starts `postgres:16`, installs `postgresql-client`, runs `Invoke-DbObjectSourceCiCheck.ps1 -RunDbApply` through direct `psql`, then `git diff --check`. |

Both jobs upload `build/reports/*` as workflow artifacts. The PostgreSQL job uses disposable CI service credentials only: `exitpass` / `change_me` against a service-container database.

## PostgreSQL service-container apply
The PostgreSQL apply job verifies:
- object-source generated SQL freshness
- full and v1.3 object-source layout validators
- `build/generated/exitpass-full-object.generated.sql` applies to a clean disposable database
- `scripts/validation/Validate-V13CentralPmsAlignment.sql` passes against that database
- report JSON/Markdown are emitted

The CI DB apply does not rely on local container names. It uses these parameters/environment values:
- `DbHost=localhost`
- `DbPort=5432`
- `DbUser=exitpass`
- `DbPassword=change_me`
- `AdminDatabase=postgres`
- `ValidationDatabase=exitpass_object_source_coverage_validation`

## What is checked
- All ExitPass-owned schemas are represented under `objects/schemas`.
- `public`, `pagila`, and system schemas are not treated as ExitPass-owned object-source schemas.
- `objects/extensions/public.pgcrypto.sql` is present.
- Object counts are reported by type.
- Apply-order files have no missing entries or duplicates.
- The full apply order covers all non-UAT object source files; UAT object files are explicitly covered by the UAT apply order.
- Full and v1.3 generated SQL artifacts have generated headers and are stable after regeneration.
- Required baseline and v1.3 object markers are present in generated SQL.
- Disposable DB apply can apply the full generated SQL and run `Validate-V13CentralPmsAlignment.sql`.

## What is not checked
- No schema behavior changes are introduced by this slice.
- No Atlas CLI dependency is required.
- No POS Server schema or application repository behavior is validated.
- No production data, secrets, certificates, raw evidence, or credentials are inspected or seeded.
